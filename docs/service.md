# Постоянная работа на личном компьютере

Сервис поддерживает работу пайплайна после закрытия терминала. Он обновляет локальную таблицу с заданным интервалом и отдельно проверяет календарь доставки писем. После перезагрузки он запускается при входе того же пользователя в Windows или macOS.

Здесь описаны [service.py](../agent_code/service.py), [runtime.py](../agent_code/runtime.py), [шаблон .env](../templates/environment.env) и [проверки](../tests/test_service.py). Начальная настройка источников описана в [README](../README.md), особенности Mac — в [дополнении для macOS](macos.md).

## Что делает каждый компонент

| Компонент | Что получает | Что делает | Что сохраняет |
|---|---|---|---|
| `service.run(root, once=False)` | Папку проекта и интервалы `[service]` | Вызывает `digest.py run`, затем в отдельном ритме `digest.py tick` | Время и результат шагов в `private/service-status.json` |
| `digest.py run` | Источники и правила пользователя | Собирает действительную сводку | `out/live/digest.html` и CSV |
| `digest.py tick` | Расписание `[schedule]` и настройки `[mail]` | Проверяет, наступил ли слот; при необходимости собирает свежую сводку и отправляет её | Штатное состояние доставки в `private/mail.sqlite` |
| `runtime.load_environment(root)` | Только `.env` данного проекта | Добавляет разрешённые значения в окружение дочернего запуска | Не создаёт журнал значений и не меняет сессии входа |
| `install(root)` | Путь проекта, его `.venv`, текущего пользователя ОС | Регистрирует и запускает пользовательский автозапуск | XML задачи Windows или plist LaunchAgent |
| `remove(root)` | Тот же путь проекта | Останавливает и удаляет его автозапуск | Сохраняет настройки, отчёты, учётные сессии и историю |
| `status(root)` | Файл состояния и межпроцессную блокировку | Отделяет живой процесс от оставшегося после него файла | Возвращает проверенный словарь без секретов |

`tick` сам проверяет необходимость отправки. Успешный `tick` может означать, что время ещё не наступило или выпуск уже был отправлен. `last_success_tick` поэтому не является подтверждением получения письма.

## Однократная проверка перед автозапуском

Откройте терминал в папке проекта и активируйте его `.venv`, как показано в README. Дальше команды одинаковы на Windows и macOS.

```text
python digest.py service --once
```

`python` запускает интерпретатор; `digest.py` — вход в проект; `service` выбирает сервис; `--once` просит выполнить только один настоящий сбор. Это обычный рабочий проход по настроенным источникам. Он не подставляет учебные сообщения и не вызывает `tick`, поэтому сам эта команда не отправляет письмо. Ошибка входа, сети или конфигурации остаётся ошибкой проверки.

```text
python digest.py status
```

`status` показывает состояние последнего прохода. Найдите `last_scan.result`: `ok` означает завершившийся сбор, `failed` — ненулевой код команды, `timeout` — превышенное ограничение времени, `start_failed` — процесс не удалось запустить, `stopped` — поступил запрос остановки. Для каждого завершившегося шага записаны начало, окончание и, если процесс запускался, код завершения.

После `--once` значение `running` будет `false`: сервис уже закончил проверку. Это нормально. Для постоянно работающего сервиса `running=true` означает занятую блокировку процесса; `responsive=true` дополнительно означает, что его пульс обновлялся не более 30 секунд назад. Пульс не доказывает доступность Telegram, LMS или почты — для этого смотрите результат нужного шага.

## Два разных расписания

Добавьте в `private/study.toml` самостоятельную секцию, если хотите изменить интервалы:

```toml
[service]
scan_interval_seconds = 900
tick_interval_seconds = 60
command_timeout_seconds = 600
```

| Поле | Смысл | Допустимый диапазон |
|---|---|---|
| `scan_interval_seconds` | Пауза между окончанием сбора и следующим сбором | 30–604800 секунд |
| `tick_interval_seconds` | Пауза между проверками календаря доставки | 10–3600 секунд |
| `command_timeout_seconds` | Максимальное время одного дочернего `run` или `tick` | 10–7200 секунд |

Если секции нет, действуют указанные выше значения. Интервалы проверяются при старте сервиса. После их редактирования перезапустите сервис.

Например, таблица обновляется каждые 15 минут, а письма должны приходить по вторникам и четвергам в 09:00. Для этого оставьте `scan_interval_seconds=900`, а дни и время задайте в уже существующей секции `[schedule]`. Параметр `[mail].enabled` отдельно включает доставку. Изменение частоты сбора не включает отправку.

Шаги выполняются последовательно. Если сбор занимает несколько минут, проверка отправки может задержаться на его время. Ограничение `command_timeout_seconds` не позволяет этому ожиданию длиться бесконечно. Сервис не обещает отправку с точностью до секунды и не создаёт очередь всех пропущенных опросов.

## Запуск, остановка и автозапуск

Для работы в открытом терминале:

```text
python digest.py service
```

Оставьте окно открытым. `Ctrl-C` попросит цикл остановиться; сервис остановит свой дочерний процесс, сохранит состояние и освободит блокировку. Это удобно для проверки подключения перед фоновой работой.

Для работы после закрытия терминала:

```text
python digest.py install-service
```

Команда действительно изменяет пользовательский автозапуск и сразу запускает сервис. Административные права не запрашиваются. Устанавливайте его только после успешного `--once`. Если уже работает запущенный вручную экземпляр, сначала остановите его через `Ctrl-C`.

```text
python digest.py remove-service
```

Команда отключает автозапуск данного экземпляра проекта. На Windows работающему сервису сначала передаётся локальный запрос остановки. Удаление не подтверждается, если сервис не успел освободить блокировку. На Mac `launchctl bootout` останавливает LaunchAgent. Удаление автозапуска не удаляет учётную сессию Telegram, вход в Codex/Claude, `.env`, отчёты или базу доставки.

Чтобы применить новые интервалы, удалить старый автозапуск и зарегистрировать его заново, последовательно выполните `remove-service`, затем `install-service`. После перемещения папки или пересоздания `.venv` также переустановите автозапуск. Лучше удалять старую регистрацию до перемещения проекта: имя регистрации зависит от его абсолютного пути.

### Windows

Создаётся задача Task Scheduler текущего пользователя с типом `InteractiveToken` и уровнем `LeastPrivilege`. Пароль Windows в задачу не записывается. Задача начинает работу при входе владельца, работает с `.venv\Scripts\pythonw.exe`, если он доступен, и с папкой проекта как рабочим каталогом. `pythonw.exe` исполняет тот же Python-код без отдельного консольного окна. `IgnoreNew` предотвращает второй запуск задачи, дополнительный `FileLock` защищает и от запуска из другого терминала.

Установщик вызывает `whoami /user /fo csv /nh`, чтобы получить SID владельца, затем `schtasks /Query`, `/Create` и `/Run`. XML сохраняется в `private/service-task.xml`. При удалении используются `/End` и `/Delete`. Все аргументы передаются напрямую, без сборки shell-строки. Перед заменой или удалением существующей задачи проверяются её владелец, действие и каталог. Сведения о [режиме входа](https://learn.microsoft.com/en-us/windows/win32/taskschd/principal-logontype), [создании](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-create) и [немедленном запуске](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-run) описаны у Microsoft.

Если организация запрещает создание задач даже для собственной учётной записи, установка завершится понятной ошибкой. Команда не пытается повышать права или обходить такую политику.

### macOS

В `~/Library/LaunchAgents` записывается plist с командой `.venv/bin/python -X utf8 -m agent_code.service run`. Параметр `RunAtLoad` запускает сервис при загрузке, `KeepAlive` просит macOS поддерживать процесс, а `ThrottleInterval=60` ограничивает частоту перезапуска. Перед загрузкой файл проверяется через `plutil -lint`.

Регистрация выполняется через `launchctl bootstrap gui/UID путь.plist`; выгрузка — через `launchctl bootout gui/UID/имя`. `UID` здесь номер текущего пользователя, программа определяет его сама. Без графического сеанса установка сообщает об отсутствии нужного домена. Она не переключается на системный daemon. Apple описывает [пользовательские LaunchAgent и их жизненный цикл](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html), а также [управление через launchctl](https://support.apple.com/en-asia/guide/terminal/apdc6c1077b-5d5d-4d35-9c19-60f2397b2369/mac).

В plist записывается путь поиска установленных программ, но значения секретов туда не копируются. Файл состояния сервиса заменяет бесконтрольные журналы stdout/stderr.

## Что хранить в `.env`

Шаблон [environment.env](../templates/environment.env) содержит пустые поля секретов. Рабочий файл называется `.env` и лежит рядом с `digest.py`. Загрузчик не ищет другие `.env` выше по дереву каталогов, не исполняет содержимое и не раскрывает `${...}` внутри значений.

| Переменные | Для чего нужны |
|---|---|
| `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` | Собственное приложение Telegram |
| `TELEGRAM_PHONE` | Необязательный международный номер, снимающий вопрос о номере при новом входе |
| `TELEGRAM_2FA_PASSWORD` | Необязательный пароль двухэтапной проверки для локального входа. Не одноразовый код; поле можно очистить после входа |
| `TELEGRAM_ALLOWED_CHAT_IDS`, `TELEGRAM_DENIED_CHAT_IDS` | Штатные ограничения чтения MCP; пустой allowlist запрещает все чаты, `*` допускает выбор доступных диалогов |
| `TELEGRAM_SESSION_DIR` | Каталог штатного хранилища Telegram-сессии |
| `TELEGRAM_WRITE_ENABLED` | Принимается только `false` |
| `DIGEST_SMTP_ADDRESS`, `DIGEST_SMTP_HOST`, `DIGEST_SMTP_PORT`, `DIGEST_SMTP_PASSWORD` | Собственный адрес, SMTP-сервер, TLS-порт и пароль приложения |
| `LMS_URL`, `LMS_TOKEN` | Необязательный API Smart LMS, если ВШЭ предоставила доступ |
| `HSE_LMS_TOKEN` | Поддерживаемое старое имя токена, которое читает `lms_api.py` |

`LMS_URL` допускает только HTTPS-сервер `edu.hse.ru`, корень или официальный REST-путь. Адаптер продолжает обращаться к своему фиксированному адресу; токен не пересылается на произвольный сайт. `LMS_TOKEN` подставляется под имя `HSE_LMS_TOKEN`, если последнее ещё не задано.

Переменные, заданные операционной системой до запуска, сохраняют приоритет: используется `override=False`. Неизвестный ключ останавливает загрузку, поэтому `.env` не может подменить `PATH`, включить запись в Telegram или добавить произвольную настройку поставщика модели. Пустые значения не экспортируются в окружение; при этом сам MCP читает свой `.env`, и пустое поле ACL сохраняет собственное значение «ничего не разрешено». Поведение приоритета окружения описано в [документации python-dotenv](https://bbc2.github.io/python-dotenv/).

Сервис не загружает `.env` в долгоживущий родительский процесс. Каждый новый `digest.py` читает файл заново, поэтому правка файла применяется к следующему сбору. Если значение задано самой ОС, изменение `.env` его не перекроет: нужно изменить исходное окружение и перезапустить сервис.

При первом входе или после отзыва сессии одноразовый код Telegram вводится владельцем в терминале. Номер и необязательный пароль 2FA можно заранее задать в `.env`; пустое поле пароля оставляет скрытый запрос. Неверный настроенный пароль требует исправления или удаления, без автоматических повторов. `telegram-login` ограничивает права файла и запускает штатный вход. При действительной сохранённой сессии вопросов нет; обычные сборы службы используют эту сессию автоматически. Изменение номера не переключает сохранённый аккаунт: при следующем `telegram-login` несовпадение вызовет ошибку. Сам сбор продолжает использовать ранее сохранённую сессию. Для другого аккаунта выберите отдельный `TELEGRAM_SESSION_DIR` и выполните вход.

Telegram читает ровно файл, выбранный в `[mcp].env_file`. Если это внешний файл, Telegram-поля корневого `.env` не экспортируются в окружение и не перекрывают его. Для API-данных действуют настоящие переменные ОС; для чатов разрешения файла и ОС пересекаются, а запреты объединяются.

`.env` остаётся обычным незашифрованным текстом. Поля номера и 2FA не нужны рабочему `serve` и не передаются ему как параметры входа; код не выводит их в статус. Авторизация Codex или Claude проходит через штатный CLI. Эти сеансы живут в своих хранилищах; `.env` их не заменяет. Не переносите их в Git и не записывайте в манифест автозапуска.

## Сбой, сон и повторный вход

- **Сон или выключение компьютера.** Код в это время не работает. После пробуждения продолжится цикл, после загрузки и входа запустится зарегистрированная задача. Сервис не будит ноутбук и не делает его сервером 24/7.
- **Выход из учётной записи.** Выбранная схема рассчитана на открытый пользовательский сеанс. После выхода её работу считать доступной нельзя; следующий вход снова запускает задачу. Блокировка экрана отличается от выхода из аккаунта.
- **Сбой отдельного сбора.** Результат записывается как `failed` или `timeout`, затем цикл продолжает работу по установленным интервалам. Предыдущее время успешного сбора сохраняется отдельно.
- **Сбой всего сервиса.** Windows настроена на три повторные попытки с интервалом в минуту. macOS управляет повторным запуском через `KeepAlive`. Если ошибка постоянная, необходимо исправить конфигурацию; автозапуск её не исправляет.
- **Истёкшая авторизация.** Сохранённая сессия позволяет автоматические проходы, пока Telegram её принимает. После отзыва или истечения фоновый процесс не получает одноразовый код и не открывает интерактивный диалог. Выполните `python digest.py telegram-login` в своём терминале. Номер и пароль из `.env` не отменяют новый код. Тексты внешних ошибок не копируются в статус.
- **Пропущенное время письма.** Действует существующее окно `[schedule].catchup_hours`. `tick` выбирает наиболее свежий подходящий слот, а база доставки препятствует повторной отправке подтверждённого выпуска. Неопределённый результат SMTP не превращается в автоматический повтор.
- **Старый `install-schedule`.** Это отдельная регистрация доставки из прежней версии практикума. При переходе на постоянный сервис удалите её штатной командой `remove-schedule`. Новый сервис не удаляет другие задачи молча.

Если `last_scan` показывает ошибку, запустите `python digest.py run` вручную в активном окружении. Прочитайте краткую диагностику и исправьте источник, доступ или настройки. Для тайм-аута проверьте число читаемых источников и доступность сети; увеличивайте лимит осознанно, поскольку он также ограничивает задержку проверки доставки.

## Как устроена реализация

1. `_options` проверяет интервалы и рабочий режим. `_python` выбирает интерпретатор именно проекта; путь symlink на Mac сохраняется, чтобы не потерять виртуальное окружение.
2. `run` захватывает `private/service.lock`, восстанавливает безопасные поля предыдущего состояния и устанавливает обработчики остановки.
3. `_execute` создаёт отдельный процесс `digest.py run` или `tick` с закрытым stdin и отброшенными stdout/stderr. Запросов интерактивного входа в фоне нет. Пульс состояния обновляется примерно раз в пять секунд.
4. После результата код записывает времена, короткий статус и код завершения. Состояние сначала пишется во временный файл, затем атомарно заменяет прежнее. На POSIX выставляются права `0600`; в Windows доступ определяется ACL вашей папки.
5. При тайм-ауте останавливается группа дочернего процесса. На Mac сначала посылается `SIGTERM`, при необходимости — `SIGKILL`; на Windows используется `taskkill /PID … /T /F` для собственного дочернего дерева. Поэтому прерванный сбор не считается завершённым.
6. При остановке освобождается файловая блокировка. При следующем старте сохраняются прежние отметки успешных шагов; библиотечные сессии и база доставки лежат отдельно от памяти процесса.

Такое разделение соответствует идеям предоставленного методического материала «Разработка и применение мультиагентных систем в корпоративной среде»: среда исполнения и мониторинг рассматриваются в §3.3, с. 46–48, отдельное устойчивое хранение состояния — в §3.5, с. 52. Здесь эти идеи реализованы в масштабе личного ноутбука. Регулярный цикл обеспечивает исполнение; рассуждение и проверяемые действия агента остаются в модулях пайплайна.

## Что проверяют тесты

```text
python -m unittest discover -s tests -p test_service.py -v
```

`-m unittest` запускает встроенный тестовый инструмент Python; `discover` ищет проверки; `-s tests` задаёт папку; `-p test_service.py` выбирает этот файл; `-v` показывает результат каждого сценария.

Проверяются приоритет и допустимые ключи `.env`, отсутствие секретов в ошибках, запрет неподдерживаемого LMS-адреса, единственный экземпляр, одноразовый сбор без доставки, независимые интервалы, сохранение последнего успеха и остановка реального тестового дочернего процесса. Манифесты Windows/macOS разбираются обратно и проверяются структурно; системные вызовы регистрации подменяются. Успех этих тестов подтверждает код и контракты команд. Он не доказывает, что автозапуск уже установлен или проверен в настоящем сеансе конкретного компьютера.
