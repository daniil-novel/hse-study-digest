# Готовые исходники агентного приложения

Эта папка расширяет существующий сборщик учебных поручений. Файлы можно читать последовательно: сначала `runtime.py`, затем `knowledge.py`, `skills.py` и `service.py`. Публичные функции содержат комментарии о входе, результате и ограничениях. Полный маршрут запуска находится в [README](../README.md), а [карта руководства](../docs/guide-mapping.md) объясняет методические основания.

## 1. `knowledge.py`: задачи, версии, Wiki и RAG

[Исходник](knowledge.py) · [подробная глава](../docs/knowledge.md) · [тесты базы](../tests/test_knowledge.py) · [сквозные проверки](../tests/test_pipeline_flow.py)

**Назначение.** Результат отдельного сбора превращается в долговременную личную базу. Хранилище — `private/knowledge.sqlite`, производные страницы — `private/wiki`. Отдельно устанавливать сервер базы данных не требуется: SQLite работает внутри Python.

### Главные функции

| Функция | Вход | Выход и действие |
|---|---|---|
| `update(rows, private, now)` | Нормализованные карточки, закрытая папка, время с часовым поясом | Сохраняет новые наблюдения и версии в транзакции, возвращает статистику |
| `current_rows(private)` | Папка базы | Последние версии с ID, отметкой выполнения, временем наблюдения и признаком доступности |
| `set_done(private, task_id, done=True)` | Существующий ID и нужная отметка | Меняет только пользовательский статус |
| `search(private, query, limit=8)` | Текст запроса и ограничение выдачи | Найденные текущие карточки со свидетельствами, без обращения к модели |
| `answer(private, query, provider)` | Вопрос и имя подписочного инструмента | Ответ и свидетельства после проверки ID, цитат и актуальности версий |
| `export_wiki(private)` | Папка базы | Список созданных Markdown-файлов по предметам и индекс |

Минимальная цепочка на настоящих данных: `run` получает карточку → `update` присваивает `K-…` и версию 1 → повторный сбор без изменений сохраняет версию 1 → изменение той же однозначно определяемой карточки создаёт версию 2 → `search` возвращает версию 2 → Wiki показывает и текущие сведения, и историю. Смысл многоточия здесь — настоящий ID, который выдаёт программа, а не значение для ручного ввода.

### Как читать код

Начните со схемы таблиц и `_normalized`. Затем прочитайте `_matches`, `update`, `_revision` и `_observe`: это различие между карточкой, изменением содержания и повторным наблюдением. После этого переходите к поиску и ответу. Названия с начальным подчёркиванием обозначают внутренние вспомогательные функции.

`tasks` хранит устойчивый ID и состояние пользователя; `versions` — неизменяемые снимки содержания; `observations` — факты чтения; `task_search` — поисковое представление только текущих версий. Для одного источника могут существовать несколько задач. Сопоставление начинается с точного содержимого, затем проверяет однозначную пару «предмет + действие». Если осталась ровно одна старая и одна новая карточка одного источника, ID сохраняется. При неоднозначности программа не делает семантическую догадку.

Непустой успешный сбор помечает отсутствующие прежние карточки `not_checked`; пустой сбор сохраняет их прежнее состояние. Ни один из этих случаев не означает отмену задания. Отметка `done` сохраняется при переносе срока.

### Что можно менять в учебной работе

Можно улучшить правила поиска, оформление Wiki или набор отображаемых полей. Изменение сопоставления версий требует проверки инвариантов: повтор не создаёт новую версию, отметка пользователя не сбрасывается, независимые источники не сливаются, пустой вход не стирает базу. Для нового признака сначала определите, меняет ли он содержание версии или только способ отображения.

FTS5 ищет слова и префиксы, нормализует `ё`/`е` и исключает часть служебных слов. Поиск не понимает все синонимы и словоформы. `answer` посылает вопрос и нормализованные найденные поля; URL и подпись источника добавляются к свидетельствам локально. В базе нет сырых Telegram-переписок. Проверка наличия точной цитаты не доказывает, что модель сделала верный вывод.

**Ошибки:** отсутствие базы означает, что нужен первый успешный сбор; неизвестный ID в `done` нельзя угадать — возьмите его из выдачи; пустой поиск требует другого слова; изменение версии во время ответа требует повторного вопроса. Файл Wiki пересоздаётся: ручные исправления в нём не являются обновлением базы.

## 2. `service.py`: постоянная работа и автозапуск

[Исходник](service.py) · [подробная глава](../docs/service.md) · [тесты](../tests/test_service.py)

**Назначение.** Процесс наблюдает за временем и запускает обычные короткие команды `digest.py run` и `digest.py tick`. Он не заменяет сборщик и не хранит пароли в своей конфигурации автозапуска.

Читайте `Options` и `_options` для настроек, `_execute` для одного дочернего процесса, затем `run` для цикла. `status` проверяет состояние и живость. `install` и `remove` управляют Task Scheduler в Windows или LaunchAgent в macOS. `_windows_xml` и `_mac_plist` формируют штатные документы ОС, а проверки `_owns_windows` и `_owns_mac` предотвращают изменение чужого задания с похожим именем.

Минимальная цепочка: `service --once` → один вызов `run` → `private/service-status.json` с результатом → завершение. В этом режиме `tick` не вызывается, письмо не отправляется. При постоянной работе отдельные интервалы определяют сбор и проверку доставки. Интервал отсчитывается после окончания предыдущей операции, поэтому медленный сбор не создаёт бесконечную очередь одинаковых процессов.

`service.lock` не даёт двум службам одной копии проекта работать параллельно. `digest.lock` защищает сами рабочие сборы. Состояние записывается атомарно и содержит безопасный итог, время и heartbeat; содержимое переписки и секреты не превращаются в лог службы. При ошибке ручной `run` позволяет получить конкретную причину. При остановке завершается и выполняемая дочерняя команда.

**Что менять:** интервалы в `[service]`, предел времени одной команды, способ отображения состояния. Не добавляйте пароли в XML/plist и не заменяйте фиксированную команду произвольной shell-строкой из текста сообщения. Для работы после сна и входа нужен реальный тест на целевой ОС. Тесты проверяют формирование документов, разбор состояния, безопасный запуск, блокировки и поведение при сбоях, но не входят за студента в аккаунты.

## 3. `runtime.py`: локальные секреты

[Исходник](runtime.py) · [пустой шаблон](../templates/environment.env) · [проверки](../tests/test_service.py)

**Назначение.** `load_environment(root)` читает только `.env` конкретной копии проекта и добавляет поддерживаемые непустые значения в окружение текущей рабочей команды. Возвращаются только имена добавленных переменных, а не их значения.

Читайте `ENV_KEYS`, `_validate` и `load_environment` в этом порядке. Перечень ключей закрыт. Файл не может изменить `PATH`, `PYTHONPATH` или произвольную настройку модели. `TELEGRAM_WRITE_ENABLED` должен быть `false`; `LMS_URL` ограничен официальным HTTPS-адресом Smart LMS. Подстановка `${…}` выключена: пароль воспринимается как текст.

Минимальная цепочка: студент заполняет `DIGEST_SMTP_PASSWORD` в корневом `.env` → следующая команда загружает значение → доставка использует его → файл отчёта и модель его не получают. Уже заданная переменная ОС имеет приоритет над `.env`. Это полезно при централизованной настройке, но важно при диагностике неожиданного старого адреса.

**Что менять:** новый секрет добавляют только вместе с определённым потребителем и проверкой назначения. Не выводите значения для отладки. Ошибка «Проверьте .env по templates/environment.env» означает неподдерживаемый ключ, формат, запрещённый адрес или режим. Сравните имена с шаблоном локально. OAuth и Telegram sessions не заменяются этим загрузчиком.

## 4. `skills.py`: переносимые инструкции

[Исходник](skills.py) · [исходные навыки](../skills)

**Назначение.** `install(provider)` копирует три навыка в проектную папку нужного инструмента; `instructions(name)` читает содержательную часть исходного `SKILL.md` для включения в программный промпт. Это два способа применять одни и те же правила работы.

`NAMES` ограничивает допустимые имена. `ROOT` определяется по расположению файла, поэтому запуск из другой папки не выбирает случайные инструкции. `install` сохраняет существующую пользовательскую копию навыка и сообщает об этом. Повторная установка не является обновлением отредактированного файла.

Минимальная цепочка: `install-skills codex` → `.agents/skills/study-search/SKILL.md` доступен агенту, запущенному из корня → студент просит найти сведения; отдельно программный `ask` читает исходную инструкцию через `instructions` и добавляет её к ограниченному вызову модели. Автоматический вызов не зависит от того, обнаружил ли интерактивный агент проектную копию.

**Что менять:** формулировки ролей и порядок проверки результата. Навык не выдаёт новых прав, не открывает исключённые чаты и не заменяет функции валидации. Новое имя требует обновления списка и соответствующего потребителя. Если изменили исходный навык после установки, сравните его с проектной копией вручную: ваши прежние правки не должны исчезать незаметно.

## Проверка изменений

Из активного окружения проекта выполните:

```text
python -m unittest discover -s tests
```

`python -m unittest` запускает встроенный механизм тестов; `discover` находит их автоматически; `-s tests` задаёт папку поиска. Полный набор проверяет также связи расширения с остальным приложением. Внешние аккаунты, реальные чаты и отправка письма в этом наборе не используются как доказательство доступности сервисов.

Для защиты покажите один фактически проверенный путь: источник → нормализованная карточка → стабильный ID → повтор/изменение → Wiki → выдача поиска. Если разрешён вызов модели, добавьте ответ со свидетельствами. Хранение состояния и автозапуск полезны инженерно, но сами по себе не являются научной новизной.
